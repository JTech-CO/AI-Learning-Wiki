_키 노출·인증 우회·입력값 검증 누락 3대 취약점을 직접 점검하고, 최소 보안 수칙을 코드에 적용한다. API 키 하나가 깃허브에 노출돼 하룻밤 사이 수백만 원 청구서가 날아오는 사고를 막는 것이 목표다._

:::note[학습 목표]
- 내 앱의 키 노출·인증 우회·입력값 검증 누락 3대 취약점을 직접 점검한다
- 하드코딩된 키를 .env로 분리하고 노출됐던 키는 폐기·재발급한다
- 서버 인증 재검증과 파라미터 바인딩·입력 검증으로 최소 보안 수칙을 코드에 적용한다
:::

## 핵심 개념

앱 보안은 대단한 해킹 방어가 아니라 **'기본 실수 3가지'를 막는 일**이에요. 첫째, 비밀 키(API 키·DB 비밀번호)를 코드나 깃허브에 그대로 두지 않기. 둘째, '로그인한 척'만 하면 통과되는 허술한 인증을 **서버에서 다시 검증**하기. 셋째, 사용자가 입력한 값을 그대로 믿지 않고 검사하기. 실제 초보 앱 해킹의 대부분은 이 세 가지 중 하나예요. 은행 금고를 뚫는 게 아니라 **열려 있는 뒷문으로 그냥 걸어 들어오는 것**에 가깝습니다.

### 왜 이게 될까?

앱 해킹의 대부분은 대단한 기술이 아니라 '열린 문'을 그냥 걸어 들어오는 것이에요. API 키가 깃허브에 그대로 남아 있거나, 서버가 '로그인했다는 말'만 믿고 데이터를 내주거나, 사용자 입력을 검증 없이 그대로 실행하면 누구나 들어올 수 있어요. 이 **세 군데 문만 잠그면** 실제 공격의 절대다수를 막습니다.

## 👀 따라하기 예시 — 주문 조회 API `/api/orders/:id` 점검

**① 노출된 키부터 검색** — 코드 전체에서 `Ctrl+Shift+F`로 `sk-` 검색 → `app.js` 12번 줄에서 `const openaiKey = "sk-proj-abc123..."` 발견.
> 💡 비밀 키는 항상 제일 먼저 잡아야 할 1순위 구멍. 코드에 박혀 있으면 언젠가 깃허브에 올라가요.

**② 키를 `.env`로 옮기고 `.gitignore`에 등록** — `.env`에 `OPENAI_KEY=sk-proj-abc123`, `.gitignore`에 `.env` 추가, 코드는 `const openaiKey = process.env.OPENAI_KEY`.
> 💡 앞으로는 키가 코드에 안 보이니 실수로 커밋될 일이 없어요. 단, 이미 노출됐던 키는 이걸로 안 끝나요(다음 단계).

**③ AI에게 인증 우회 여부 점검 요청** — "이 엔드포인트가 로그인·본인 확인 없이 데이터를 반환하는지 점검해줘" → `req.query.user_id`를 그대로 믿던 부분을 세션의 `user_id`와 대조하도록 고침.
> 💡 프론트에서 로그인 체크한다고 안심 금물. 서버가 '이 요청 진짜 이 사람 데이터 맞아?'를 매번 다시 확인해야 진짜 잠긴 문이에요.

**④ 직접 찔러보는 셀프 침투 테스트** — `/api/orders/1001`을 `/api/orders/1002`로 바꿔 호출 → 수정 전엔 남의 주문이 그대로 보임 → 소유자 검증 추가 후 재시도하니 `403 Forbidden`.
> 💡 고쳤다고 믿지 말고 공격자처럼 직접 두드려봐야 진짜 막혔는지 확인돼요. 이게 제일 확실한 증거.

좋은 결과의 기준: (1) 코드·이력 어디에도 실제 키 문자열이 없다 (2) 남의 id로 요청하면 403이 뜬다 (3) 사용자 입력이 쿼리에 그대로 이어붙지 않고 파라미터 바인딩된다.

## 단계별 따라하기

1. **내 코드에 숨은 비밀 키 색출하기** — 프로젝트 폴더 전체에서 `API_KEY`, `SECRET`, `password`, `sk-`, `token` 검색. 코드 파일(`.js` `.ts` `.py` `.env` 포함)에 실제 키가 하드코딩돼 있으면 전부 표시. (에디터 `Ctrl+Shift+F` → `sk-` → `app.js` 12번 줄 `const openaiKey = "sk-proj-abc123..."` 즉시 제거 대상)
2. **키를 `.env`로 옮기고 깃에서 차단하기** — 찾아낸 키를 코드에서 지워 `.env`로 옮기고 `.gitignore`에 `.env` 한 줄 추가해 깃허브에 절대 안 올라가게. 코드는 `process.env`로 불러옴. (`.env`: `OPENAI_KEY=sk-proj-abc123` / `.gitignore`에 `.env` / 코드: `process.env.OPENAI_KEY`)
3. **노출됐던 키는 무조건 폐기·재발급** — 이미 깃허브에 한 번이라도 올라간 키는 지워도 이력에 남아 안전하지 않음. 서비스(OpenAI·Supabase 등) 대시보드에서 revoke하고 새 키 발급해 `.env`에. (OpenAI 대시보드 → API keys → 노출된 키 옆 Revoke → Create new secret key → 새 키를 `.env`에만)
4. **인증을 서버에서 다시 검증하기** — '프론트엔드에서 로그인 여부 판단' 코드는 우회됨. 민감한 데이터를 주는 API마다 서버에서 세션·토큰 확인하고 남의 데이터를 요청하면 거부. (AI에게 라우트 코드 붙여넣고 '로그인·본인 확인 없이 데이터를 반환하는지 점검' → `user_id`를 요청 파라미터로 그냥 믿던 코드를 세션의 `user_id`와 대조하도록 수정)
5. **입력값 검증·이스케이프 붙이기** — 사용자가 보내는 값(폼·URL·검색어)에 길이·형식 제한을 걸고, DB 쿼리는 문자열 이어붙이기 대신 파라미터 바인딩.
6. **셀프 침투 테스트로 확인** — 공격자 입장에서 직접 찔러봄. 로그인 없이 API 호출, URL의 id를 남의 번호로 변경, 검색창에 따옴표·스크립트 태그 삽입. 통과되면 안 됨. (`/api/orders/1001` → `/api/orders/1002`로 바꿨더니 남의 주문이 보임 → 소유자 검증 추가 후 재시도하면 403)

입력값을 쿼리에 이어붙이는 위험한 코드와, 파라미터 바인딩으로 막은 안전한 코드 비교:

```js
// 위험: 문자열 이어붙이기 → SQL 인젝션에 노출
db.query("SELECT * FROM users WHERE email='" + input + "'")

// 안전: 파라미터 바인딩 + 이메일 형식·최대 100자 검증
db.query("SELECT * FROM users WHERE email=$1", [input])
```

## 완료 체크리스트

- ☐ 코드 전체 검색으로 하드코딩된 키·비밀번호를 0건으로 만들었다
- ☐ `.env`로 키를 옮기고 `.gitignore`에 `.env`를 추가했다
- ☐ 과거 노출된 키는 폐기하고 새 키로 재발급했다
- ☐ 민감한 API마다 서버에서 로그인·본인 확인을 넣었다
- ☐ URL의 id를 남의 번호로 바꿔보고 남의 데이터가 안 보이는지 직접 테스트했다

## 흔한 실수 → 교정

- ✗ 키를 코드에서 `.env`로 옮기고 안심. 하지만 이미 깃허브에 커밋된 이력에 그대로 남아 있음 → **과거에 노출된 적 있는 키는 반드시 서비스 대시보드에서 폐기(revoke)하고 새로 발급.** `.env` 분리는 '앞으로'만 지켜주지 '과거'는 못 지웁니다.
- ✗ 프론트엔드에서 `if(로그인됨)` 체크만 하고 API는 아무나 호출할 수 있게 열어둠 → **프론트 검증은 UI 편의일 뿐. 민감한 데이터를 주는 모든 서버 API에서 세션·토큰과 데이터 소유자를 다시 확인.**
- ✗ 사용자 입력을 쿼리 문자열에 그대로 이어붙여 SQL 인젝션에 노출 → **문자열 연결 대신 파라미터 바인딩(`$1`, `?` 등)을 쓰고 입력마다 형식·길이 검증.** ORM을 쓰면 대부분 자동 처리.
