_실패 사례를 표로 모아 프롬프트를 코드처럼 디버깅한다. 반복되는 문제를 유형으로 묶어 한 번에 하나씩 규칙으로 고치고, 같은 입력으로 재검증·A/B 비교해 더 나은 버전을 근거와 함께 고른다._

:::note[학습 목표]
- 실패한 출력 5건을 입력·기대·실제·문제 열의 표로 모아 반복 패턴을 찾는다
- 한 번에 규칙 하나만 바꿔 고치고 같은 5건으로 재검증(회귀 테스트)한다
- 원본(A)과 수정본(B)을 정해둔 기준으로 세어 비교해 더 나은 버전을 근거와 함께 고른다
:::

## 핵심 개념

프롬프트 개선은 영감이 아니라 **실험**이에요. 좋은 답 하나만 보면 "이제 됐다"고 착각하지만, **실패한 답을 여러 개 모아보면** "무엇이 반복적으로 어긋나는지" 패턴이 보여요. 그 패턴을 하나씩 프롬프트 규칙으로 바꾸는 것이 **디버깅**이고, 바꾼 뒤 같은 입력들로 다시 돌려보는 것이 **회귀 테스트**예요. 소프트웨어 QA가 버그 리포트를 모아 고치듯, 프롬프트도 **실패 로그 → 가설 → 수정 → 재검증**의 폐루프로 다듬어요. 감으로 한 번에 고치려 하지 말고, **한 번에 하나씩** 바꿔 원인을 특정하세요.

### 왜 이게 될까?

AI는 규칙을 "한 번에 다 알아서" 지키지 못해요. 대신 실패 사례를 모아 패턴을 짚어주면, 그 패턴 하나를 프롬프트 규칙 한 줄로 바꿔 넣을 때마다 **정확히 그만큼** 좋아져요. 코드 버그를 하나씩 고치듯 프롬프트도 실패 로그 → 규칙 추가 → 재검증을 반복하면, **왜 좋아졌는지까지** 설명할 수 있게 됩니다.

## 👀 따라하기 예시 — 뉴스 3문단 요약 (5번 돌렸더니 계속 너무 길고 톤도 가벼움)

**① 실패 사례 5건을 표로 모은다** — 입력 '이 문장 요약해줘: (뉴스 3문단)' / 기대 '2문장' / 실제 '6문장 + 이모지' / 문제 '너무 길고 톤이 가벼움' — 이런 행이 5개.

| 입력 | 기대 | 실제출력 | 무엇이 문제 |
|---|---|---|---|
| 이 문장 요약해줘: (뉴스 3문단) | 2문장 | 6문장 + 이모지 | 너무 길고 톤이 가벼움 |

> 💡 좋은 답 말고 실패만 모아야 무엇이 반복되는지 보여요.

**② 실패를 유형으로 묶는다** — 유형A 길이 초과(3건) / 유형B 톤이 캐주얼(2건).
> 💡 유형을 나누면 어디부터 손댈지 우선순위가 생겨요.

**③ 가장 잦은 유형 1개만 고친다** — 프롬프트 끝에 한 줄 추가: `반드시 2문장 이내, 각 문장 40자 이내로 요약한다.`
> 💡 한 번에 하나만 바꿔야 뭐가 효과였는지 원인을 알 수 있어요.

**④ 같은 5건으로 재검증 + A/B 비교** — 재실행하니 길이 문제 3건 중 3건 해결. 원본(A) vs 수정본(B)을 나란히 놓고 기준(2문장 이내) 충족 여부로 세보니 B가 4승 1무 → B 채택.
> 💡 1건 성공은 운일 수 있으니 처음 그 5건 전체로, 그리고 기준을 정해 세어서 판단해야 확실해요.

좋은 결과의 기준: (1) 겨냥한 유형이 재검증에서 대부분 해결됐는가 (2) A/B를 느낌이 아니라 정해둔 기준(길이·정확·톤)으로 세어 골랐는가 (3) '무슨 실패 → 어떤 규칙 → 몇 건 개선'이 한 줄로 기록됐는가.

## 단계별 따라하기

1. **실패 사례 5건 수집** — 현재 프롬프트를 실제로 5~10번 돌려서 마음에 안 드는 출력 5건을 그대로 복사해 표로. 열은 입력·기대·실제출력·무엇이문제. 좋은 답은 넣지 말고 **실패만** 모은다. (입력 '이 문장 요약해줘: (뉴스 3문단)' / 기대 '2문장' / 실제 '6문장 + 이모지' / 문제 '너무 길고 톤이 가벼움')
2. **실패를 유형으로 묶기** — 모은 5건을 보고 반복되는 문제를 2~3개 유형으로 이름 붙인다. AI에게 표를 붙여넣고 '실패 유형을 분류해줘'라고 시켜도 좋다. (유형A 길이 초과(3건) / 유형B 톤이 너무 캐주얼(2건) / 유형C 핵심 숫자 누락(1건))
3. **가장 잦은 유형 1개만 고치기** — 제일 많이 나온 유형 하나만 겨냥해 프롬프트에 규칙 한 줄을 추가한다. **한 번에 여러 개 고치지 마라.** 원인 특정이 안 된다. (유형A 대응으로 프롬프트 끝에 '반드시 2문장 이내, 각 문장 40자 이내로 요약한다.' 추가)
4. **같은 5건으로 재검증** — 수정한 프롬프트를 1단계의 동일한 입력 5건에 다시 돌려 표의 '실제출력' 열을 갱신한다. 고쳐졌는지, 새 문제가 생겼는지. (재실행 결과 길이 문제 3건 중 3건 해결, 대신 톤 문제는 그대로 → 유형A 클리어, 유형B는 다음 반복으로)
5. **A/B 두 버전 나란히 비교** — 원본(A)과 수정본(B)을 같은 입력에 각각 돌린 출력을 좌우로 붙여놓고 승자를 표시한다. AI에게 심판을 맡기되 기준(길이·정확·톤)을 명시. (입력3에서 A=6문장 / B=2문장 → 기준 '2문장 이내' 충족은 B. 5건 중 B가 4승 1무 → B 채택)
6. **개선 로그 남기고 다음 유형 반복** — '무슨 실패 → 어떤 규칙 추가 → 몇 건 개선'을 한 줄로 기록하고 남은 유형B로 3~5단계를 반복한다. 로그가 곧 프롬프트 변경 이력. (v1→v2: 길이초과 → '2문장 이내' 추가 → 3/3 해결. v2→v3: 캐주얼톤 → '정중한 뉴스체 유지' 추가 예정)

## 흔한 실수 → 교정

- ✗ 한 번에 규칙 여러 개를 동시에 추가 → **한 반복(iteration)에 규칙 하나만 바꾼다.** 그래야 어떤 규칙이 효과였는지 원인을 특정할 수 있다.
- ✗ 잘 나온 답 하나만 보고 '고쳐졌다'고 판단 → **항상 처음 모은 동일 입력 5건 전체로 재검증한다.** 1건 성공은 운일 수 있다.
- ✗ A/B를 '느낌상 B가 낫다'로 대충 고름 → **길이·정확·톤 같은 측정 가능한 기준을 미리 정하고** 기준별 승패를 세어 다수결로.

## 실전 프롬프트

### 실패 사례 분류기 (가장 먼저)

```text
아래는 내 프롬프트가 만든 실패 출력 5건이야. 각 건의 '입력 / 실제출력 / 내가 불만인 점'을 표로 정리했어. [실패 5건]. 이 실패들을 2~3개의 반복 유형으로 분류하고 각 유형에 이름과 발생 건수를 붙여줘. 그리고 가장 먼저 고쳐야 할 유형 1개를 이유와 함께 추천해줘.
```

> 확인된 작성 예시 없음

`프롬프트 디버깅` `실패 로그` `유형 분류`

### 규칙 한 줄 제안기

```text
내 현재 프롬프트는 다음과 같아: "[현재 프롬프트]". 이 프롬프트에서 '[고칠 유형: 길이 초과]' 문제가 반복돼. 이 문제 하나만 해결하는 '규칙 한 줄'을 3가지 다른 표현으로 제안해줘. 각 안이 왜 효과 있을지 한 줄로 설명하고, 다른 문제를 새로 만들지 않는지도 점검해줘.
```

> 확인된 작성 예시 없음

`프롬프트 디버깅` `규칙 추가` `한 번에 하나씩`

### A/B 심판 (기준 명시형)

```text
같은 입력에 대해 두 프롬프트 버전의 출력이야. 입력: [입력] / A(원본) 출력: [A출력] / B(수정본) 출력: [B출력]. 다음 기준으로만 채점해줘: 1) 길이 2문장 이내 2) 핵심 숫자 포함 3) 정중한 뉴스체. 각 기준별로 A/B 중 승자와 이유를 표로 주고 종합 승자를 골라줘. 감상 말고 기준 근거만.
```

> 확인된 작성 예시 없음

`A/B 비교` `심판` `기준`

### 회귀 테스트 러너

```text
아래 5개 입력에 대해 이 프롬프트로 각각 답해줘. 답만 번호 붙여 5개, 다른 말 없이. 프롬프트: "[수정한 프롬프트]" / 입력1: [..] / 입력2: [..] / 입력3: [..] / 입력4: [..] / 입력5: [..]
```

> 확인된 작성 예시 없음

`회귀 테스트` `재검증` `일괄 실행`
